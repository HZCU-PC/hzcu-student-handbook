# P1 扩写 · 写作原则（不规定句式）

> 弹窗仍用 JSON 三个字段 `solve` / `method` / `impact`（UI 三块），**只约束内容与诚实口径，不约束开头、段落套路或 hook 格式**。

## 原则

1. **怎么写都行** — 叙述、问答、对比、故事、列表混写均可；不必「先问题后方法后影响」的论文摘要体。
2. **hook** — 可选风格：人话半句、术语、提问、空白；**不要**统一成 slogan 或「X：Y＋Z」标题体。
3. **事实与口径** — 仍须：不夸大；无正式论文/无 peer review 的条目如实标注；数字注明来源（论文/官方/第三方）；争议与局限可以写，**不必**套固定收尾句（如「局限是…」「不能说明…」可自然融入，也可不写）。
4. **字段分工 loosely** — 三块大致对应「读者为啥关心 / 做了什么 / 后来怎样」，但**允许重叠、允许某块很短、允许某块用类比占满**；禁止为了填三块而硬拆。
5. **禁止的是套话，不是结构** — 见下「避免」；没有「必须包含」的句式清单。

## 避免（反范式，非替代表达）

- 批量使用同一开头（如连续多篇「X 探索能否…」「核心问题是…」「2023 年…差距明显」）。
- 尚未替换干净的旧模板：`核心问题，是如何在…条件下…`（应改写为真实内容，不是换同义模板）。
- 空洞抬升：「具有重要意义」「推动快速发展」且无具体所指。
- hook 与正文完全无关的营销句。

## 批次交付（CDX / WKB）

- `scripts/batchNN_*.py` 只 patch JSON；**不要**在脚本注释里写「solve 必须…」「impact 必须局限句」。
- log 里列 id 与核对事实即可；**不要**附「写作模板例句」。

## UI 说明

字段名仍是 solve/method/impact；若日后改弹窗标题（背景/做法/后来），与本文独立。
